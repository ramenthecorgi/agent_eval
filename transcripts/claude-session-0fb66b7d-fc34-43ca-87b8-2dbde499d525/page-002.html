Here are three approaches:

Option A — Flat, explicit instrumentation Everything lives in a small number of files. The agent loop, guardrails, and tracer are all functions called in sequence with explicit tracer.emit(event) calls inline. Simple to read, zero indirection, but guardrails are hard to extend (adding LLM-based checks means editing core agent code).

Option B — Layered modules with a Guardrail protocol (Recommended) Separate modules for agent, tools, guardrails, tracer, and api. Guardrails implement a simple protocol with check_request() / check_response() methods — today's RuleBasedGuardrail can be swapped or chained with a future LLMGuardrail without touching agent logic. The tracer is a dedicated class that writes lifecycle events to JSON session files. FastAPI serves both the API and the static frontend. Clean boundaries, easy to test each piece in isolation.

Option C — Middleware-based tracing FastAPI middleware handles high-level events (request in, response out), while the agent emits lower-level events (tool calls, LLM calls). Two separate tracing paths that need to be stitched together by session ID. More "framework-native" but creates coordination complexity between middleware and agent-level events.

I recommend Option B. The Guardrail protocol gives you the extensibility hook you explicitly asked for, the layered modules are easy to reason about independently, and a single tracer class keeps all event emission in one place. Option C's split-tracing model adds complexity for no real benefit at this scale.

Does this direction work for you?

Let me walk through the design section by section.

Architecture

agent_eval/
├── backend/
│   ├── main.py            # FastAPI app, mounts static files
│   ├── agent.py           # Agentic loop (Claude tool-use)
│   ├── tools.py           # search_wikipedia implementation
│   ├── guardrails.py      # Guardrail protocol + RuleBasedGuardrail
│   ├── tracer.py          # Tracer class, session JSON writer
│   └── traces/            # One JSON file per session
└── frontend/
    ├── index.html          # Chat UI
    └── traces.html         # Trace viewer

A single FastAPI process serves both the REST API (/api/chat, /api/traces) and the static frontend files. No separate frontend server needed.

Does this structure look right?

Backend Flow

A single POST /api/chat request goes through this pipeline:

request → RuleBasedGuardrail.check_request()
        → Agent loop:
            → llm_request (emit trace event)
            → Claude Haiku 4.5 call
            → llm_response (emit trace event)
            → [if tool_use] tool_call (emit) → search_wikipedia → tool_result (emit)
            → repeat until final text response
        → RuleBasedGuardrail.check_response()
        → final_answer (emit trace event)
        → return to frontend

The Guardrail protocol defines two methods: check_request(text) -> GuardrailResult and check_response(text) -> GuardrailResult. GuardrailResult carries passed: bool, reason: str, and metadata: dict — leaving room for an LLM-based guardrail to populate richer metadata without changing the interface.

Does this flow make sense?
