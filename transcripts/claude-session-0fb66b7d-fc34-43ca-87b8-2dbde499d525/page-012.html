Good question. Condition 3 is the hardest to operationalize because "answerable from training" is vague. Let me think through what concrete signals make it verifiable:

Option A — query-side signals only The judge looks only at the query and asks: is this a single stable fact, a basic definition, or a well-known constant? Concrete signals: - Single entity, single attribute (height, date, name) - Answer is canonical and unlikely to vary across sources - No synthesis across multiple factors required

Simple to prompt, but the judge might disagree with itself across runs since it's making a subjective call about what "well-known" means.

Option B — response-side verification The judge looks at the actual response and asks: does the answer contain specific claims that go beyond what a well-trained model would reliably know? If the agent didn't call the tool and made specific claims, does the judge believe those claims are accurate?

This is stronger — you're verifying the outcome, not predicting capability. But it requires the judge to have ground truth, which it may not always have.

Option C — both combined Query side sets the expectation (is this the type of question training handles?), response side verifies the outcome (did the answer hold up?). More robust but two-step.

My instinct: Option B is more honest. Condition 3 isn't really about query type — it's about whether skipping the tool produced a trustworthy answer. The judge reads the response and asks: "are these claims accurate and complete, or did not searching hurt the answer?"

That's a strong idea. Instead of asking the judge to guess what Claude "knows", you make it empirical:

  1. Run the query with tools enabled → get response_with_tool (already in the trace)
  2. Run the same query against a raw Claude call with no tools → get response_without_tool
  3. Show both to the judge and ask: does the tool-enabled version add meaningful accuracy, depth, or correctness that the no-tool version lacks?

If yes → tool call added value → correct to have called it If no → responses are equivalent → tool call was unnecessary

This removes the subjectivity entirely. Condition 3 becomes: "did the no-tool response hold up?" — a comparison judgment rather than a prediction.

Tradeoffs worth noting: - Costs one extra LLM call per eval case to generate response_without_tool - The comparison judgment is still an LLM call, so you have two extra calls per case total - For guardrail-blocked cases, response_without_tool doesn't apply — those are N/A

But this is fundamentally more rigorous than any heuristic. It also naturally handles the priority order you care about: the judge doesn't need to decide abstractly whether training "should" be sufficient — it just looks at whether it was sufficient.

Judge 2: Factual Accuracy

This judge asks: are the claims in the response actually true? It's independent of sourcing — whether the answer came from Wikipedia or training doesn't matter here, only correctness.

What the judge receives: - query - actual_response

Proposed binary rubrics:

# Rubric Question asked to judge
R1 key_claims_correct Are the main factual assertions in the response correct?
R2 specifics_accurate Are specific details — names, dates, numbers, measurements — accurate?
R3 no_overconfident_errors Does the response avoid stating uncertain or wrong things as definitive fact?

Pass/fail: passed = R1 and R2 and R3

Output:

  "specifics_accurate": false,
  "no_overconfident_errors": true,
  "passed": false,
  "reasoning": "States Eiffel Tower is 330m but the correct height is 324m."
}

One thing to note: this judge is limited by the LLM judge's own knowledge. For obscure topics it may not be able to verify R2 confidently — in that case the reasoning field should say so explicitly rather than guess.
