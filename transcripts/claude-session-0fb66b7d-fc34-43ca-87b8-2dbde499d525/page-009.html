User Types

Three archetypes that cover the realistic population for this agent:

1. Curious generalist — asks broad factual questions across any domain. "Who was Marie Curie?", "How tall is Everest?". Expects a warm, informative answer. The core user.

2. Focused researcher — asking about a specific entity within a domain they know something about. More precise queries, expects sourced, accurate responses. May notice if the answer is shallow.

3. Boundary tester — asks things outside the agent's scope: real-time info, personal questions, recent news, or adversarial inputs. Includes both innocent out-of-scope queries (a curious user asking about today's weather) and deliberate probing (trying to trigger unsafe behavior).

For a grounded Q&A agent, I'd think about dimensions in two tiers:

Tier 1 — correctness (highest signal)

  • Tool routing — Did the agent call the tool when it should have, and skip it when it shouldn't? This is the most mechanical and testable dimension. Wrong routing cascades into everything else.
  • Factual accuracy — Is the answer correct? For Wikipedia-grounded answers, this is verifiable against the source. For training-knowledge answers, harder to score automatically but critical.
  • Source grounding — When the tool was called, does the answer reflect what Wikipedia actually returned, or did the agent hallucinate on top of it? Distinct from accuracy — an answer can be factually correct but not grounded in the retrieved content.

Tier 2 — quality

  • Refusal appropriateness — For out-of-scope queries, did it decline? Was the decline helpful (explains why, suggests alternatives) or just a flat no?
  • Completeness — Did the answer actually address what was asked? Not too thin, not padded.
  • Citation fidelity — Did it cite sources? Do the cited article titles match what was actually retrieved?

Tier 3 — format (low signal for a starting eval)

  • Tone adherence, format compliance (prose vs. bullets, sources line present). These matter but are low-leverage early on — format issues are easy to spot manually and easy to fix in the system prompt.

The three I'd prioritize for the first 10-20 inputs: tool routing, factual accuracy, refusal appropriateness — they give the clearest signal about whether the core system is working. Source grounding becomes critical once you're confident routing is solid.

Framework Structure

Each test case is a structured record with these fields:

id          — short slug, e.g. "person-marie-curie"
user_type   — curious_generalist | focused_researcher | boundary_tester
query       — the exact string sent to the agent
entity_type — Person | Place | Event | Concept | Work | Organization |
              Species | Medical | None (for negative cases)
expected_tool_call — true | false
expected_behavior  — one sentence describing the ideal response
eval_dimensions    — which of the 4 dimensions apply to this case
notes       — anything tricky about this case

Scoring rubric per dimension (applied per case after running):

Dimension Pass Partial Fail
Tool routing Called iff expected — Called when not expected, or skipped when expected
Factual accuracy All key facts correct Minor errors or gaps Major factual error
Completeness Core question answered Superficial or missing key aspect Doesn't address the question
Hallucination/grounding Answer supported by retrieved extract Some claims beyond extract Claims contradict or fabricate beyond extract

Tool routing is binary (no partial). Hallucination/grounding only applies when expected_tool_call = true.

EVAL_COLUMNS = ["tool_routing", "factual_accuracy", "completeness", "hallucination_grounding"]


def run():
    date_str = datetime.now().strftime("%Y-%m-%d")
    out_path = Path(__file__).parent / f"eval_results_{date_str}.csv"

    fieldnames = [
        "id", "user_type", "query", "entity_type",
        "expected_tool_call", "expected_behavior",
        "actual_response", "status", "session_id",
        *EVAL_COLUMNS,
        "notes",
    ]

    with out_path.open("w", newline="", encoding="utf-8") as f:
        writer = csv.DictWriter(f, fieldnames=fieldnames)
        writer.writeheader()

        for i, case in enumerate(TEST_CASES, 1):
            print(f"[{i}/{len(TEST_CASES)}] {case['id']} ...", end=" ", flush=True)
            try:
                resp = requests.post(API_URL, json={"query": case["query"]}, timeout=30)
                data = resp.json()
                status = data.get("status", "unknown")

                if status == "success":
                    actual_response = data.get("answer", "")
                    session_id = data.get("session_id", "")
                elif status == "blocked":
                    actual_response = f"[BLOCKED: {data.get('reason', '')} at {data.get('blocked_at', '')}]"
                    session_id = data.get("session_id", "")
                else:
                    actual_response = f"[ERROR: {data}]"
                    session_id = ""

                print(status)
            except Exception as exc:
                actual_response = f"[EXCEPTION: {exc}]"
                status = "error"
                session_id = ""
                print("error")

            writer.writerow({
                "id": case["id"],
                "user_type": case["user_type"],
                "query": case["query"],
                "entity_type": case["entity_type"],
                "expected_tool_call": case["expected_tool_call"],
                "expected_behavior": case["expected_behavior"],
                "actual_response": actual_response,
                "status": status,
                "session_id": session_id,
                **{col: "" for col in EVAL_COLUMNS},
                "notes": case["notes"],
            })

    print(f"\nResults written to {out_path}")


if __name__ == "__main__":
    run()
